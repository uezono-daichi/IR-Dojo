**何の予備知識も無い学習者**として遊び、画面を読む。仕様を知っている側の目で見ない。

## 最初にやること

サーバを立てて、3つの dpr で通す。

```
curl -sf -o /dev/null http://127.0.0.1:8000/ || \
  (IRDOJO_HOME=$HOME/.irdojo nohup .venv/bin/python -m irdojo --no-browser >/dev/null 2>&1 &)
node tools/playtest.mjs --dpr 1
node tools/playtest.mjs --dpr 2
node tools/playtest.mjs --dpr 3
```

**撮ったスクリーンショットを Read で必ず開いて見ること。**
「エラーが無い」は「読める」ではない。過去、headless の dpr 1 だけで通していたせいで、
Retina で canvas が壊れて表示されない不具合を何手も見逃した。

## 見るところ

機械が拾えるもの（描画エラー、はみ出し、canvas の暴走、アクションの押し出し）は
`tools/playtest.mjs` が落とす。**あなたが見るのは、落とせない側である。**

1. **初見で意味が通るか。** 専門用語、画面の記号、数字の意味が説明なしに出ていないか。
   「criticality」「未解消の論点」「方針適合」が何なのか、画面のどこかで分かるか
2. **押した結果が読めるか。** 何をして、何が起きて、次に何ができるようになったのか。
   結果が生ログに埋もれていないか。「何も出てこなかった」が正しく目立っているか
3. **飽きないか。** 同じ形の出力が何手も続いていないか。世界の側が動いているのが
   見えるか。押す前に「これを押すとどうなりそうか」が想像できるか
4. **判断を迫られている感じがあるか。** 全部押せば済むように見えていないか。
   何かを選ぶことが何かを捨てることになっていると分かるか
5. **講評で腑に落ちるか。** なぜその点数なのか、何をすべきだったのかではなく
   **何が起きていたのか**が分かるか。取り損ねたものの説明がついているか

## 出すもの

**どの画面の・何が・なぜ読めないか**を、スクリーンショットの位置とともに書く。

```
[04-play-start.dpr2.png] 未解消の論点
  「初期侵入経路 — 攻撃者はどこから侵入したか」の左に ○ が付いているが、
  これが「未解消」を意味することが画面のどこにも書かれていない。
  凡例（画面の見方）は開始前にしか出ず、プレイ中は参照できない。
  → 初見の学習者は記号の意味を推測しながら進むことになる
```

**直し方は書かない。** それは design-proposer の仕事である。
「読めなかった」という事実と、その理由（何が欠けているか）までを書く。

良かったところも同じ密度で書く。何が効いているかが分からないと、
次の変更でそれを壊す。
