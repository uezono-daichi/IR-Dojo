承認された設計変更を、**一貫した状態になるまで**実装する。

## 一貫した状態とは

変更が以下の**すべて**に反映されていること。どれか1つでも欠けたら未完了。

1. **実装**（`irdojo/` / `web/`）
2. **シナリオ**（`scenarios/*.yaml`）— 新しい仕組みは実際に使われていること
3. **ローダの検証** — 新しい仕組みを間違って使ったシナリオを拒否すること
4. **テスト** — 変更が守っている性質を、機械が見張る形にすること
5. **SPEC.md** — 節を書き、changelog に1行足し、版を上げる
6. **測定** — `tools/balance.py` と `node tools/playtest.mjs --dpr 2`

## 終わる前に必ず

```
.venv/bin/python -m pytest -q tests/
.venv/bin/python tools/balance.py
node tools/playtest.mjs --dpr 2
```

**落ちたまま報告しない。** 落ちた項目があるなら、直すか、
なぜ直さないかを述べる（例: 「この案は評価軸を1本増やすので範囲外」）。

## 実装のときの癖（過去に踏んだもの）

- **判定が2箇所にあることを疑う。** 「何も出てこなかった」の判定は
  エンジン（`ActionOutcome.empty`）と画面（`renderResult`）の両方にあった。
  片方だけ直して、緑の完了メッセージの下にオレンジの「何も出てこなかった」が並んだ
- **編集スクリプトは小さく分ける。** 途中の `assert` が落ちると
  そのスクリプトの編集が**全部**失われる。一度これで画面が壊れた状態が残った
- **描画は画面を表示してから。** `clientWidth` が 0 のまま canvas / SVG を描かない。
  同じ失敗を2回した（被害グラフと構成図）
- **canvas は dpr 2 で確認する。** `canvas.height` への代入は属性そのものを
  書き換えるので、読み直すと毎回積算される。dpr 1 では絶対に表面化しない
- **巨大な文字列を assert に入れない。** pytest が差分を描こうとして固まる

## テストの書き方

**何を守っているか**を docstring に書く。値の確認ではなく性質の確認にする。

```python
def test_notice_prevents_only_what_has_not_happened(scenario):
    """周知が効くのは打ち終わった時刻から先だけ。

    書いている 15分の間に現場が動いてしまうことはあるし、
    既に起きたことは戻らない。
    """
```

**壊れ方が分かるテスト**にする。過去、機械的なテストが
私が見落としていた4件目のグループ誤りを見つけた。あれが価値である。

## SPEC の書き方

**なぜそうしたかを書く。** 何をしたかだけの節は、次に読む人が
安全に変えられない。過去に間違えた指示は、間違いだったことごと書く
（「全アクション合計コストの4〜5割という指示が誤りだった」）。

changelog は1行にまとめる。長くなってもいいので、**判断の理由**を落とさない。
