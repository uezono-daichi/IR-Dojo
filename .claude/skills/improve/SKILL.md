# 一巡ぶん良くする

評価 → 案 → 実装 → 検証を1周する。**1周で扱うのは1〜2件**。
たくさん直すより、直したことの効果が測れる方が価値がある。

## 手順1. 現状を測る（並列）

3つを**同時に**投げる。互いに独立で、待ち合わせる理由が無い。

- `balance-analyst` — 設計の均衡を数字で
- `playtest-critic` — 実際に遊んで、読めない・飽きるところを
- `leak-auditor` — 答えが漏れていないか

引数には**今回の関心**を渡す。無ければ「全般」でよい。
利用者が具体的な不満を言っているなら、それをそのまま渡す
（「アクションを押した後の結果が分かりにくい」など）。

サーバが要る:

```
curl -sf -o /dev/null http://127.0.0.1:8000/ || \
  (IRDOJO_HOME=$HOME/.irdojo nohup .venv/bin/python -m irdojo --no-browser >/dev/null 2>&1 &)
```

## 手順2. 何を直すかを決める

3つの報告を読み、**利用者に見せる**。このとき:

- 見つかったものを全部並べない。**効きそうな順に3件まで**
- それぞれ「何が起きているか」「なぜそうなるか」を1〜2行で
- 数字があるものは数字で

**利用者が既に不満を言っている場合、それを最優先にする。**
測定が別のことを指していても、言われたことを勝手に降格しない。

## 手順3. 案を出す

`design-proposer` に、選んだ問題と、手順1で得た**原因の分析**を渡す。
症状だけ渡すと症状に対処する案が返ってくる。

返ってきた案の**推し**を利用者に見せ、進めてよいか確かめる。
案が設計思想に触れる（採点の重み、フェーズ構成、評価軸を増やす）ときは必ず確かめる。
画面の見せ方や文言の調整なら、確かめずに進めてよい。

## 手順4. 実装する

`spec-implementer` に、承認された案を渡す。**一貫した状態**まで持っていかせる
（実装・シナリオ・ローダ検証・テスト・SPEC・changelog）。

## 手順5. 効いたかを測る

`balance-analyst` をもう一度、画面を触ったなら `playtest-critic` も。
**手順1の数字と並べて出す。** 「良くなったはず」で終わらせない。

効いていなければ、それを言う。取り消すか、次の案に行くかを利用者に決めてもらう。

## 手順6. 残す

```
git add -A
git commit   # なぜそうしたかを書く。CLAUDE.md のコミット規約に従う
git push
```

**1周を1コミットにする。** 何が効いて何が効かなかったかが後から辿れる。

## この周で扱わないこと

- **測定側を緩めて数字を良くする。** プレイ像は「実在の学習者がそう振る舞うか」
  だけで決める（`.claude/agents/balance-analyst.md`）
- **演出を足して単調さに対処する。** 盤面を変えないものはノイズになる
- **情報を足して分かりにくさに対処する。** 足すなら何かを減らす
- **評価軸を増やす。** 報告の適時性のような新しい軸は SPEC 9.3 の範囲外

## 既知の宿題

`tools/balance.py` が現在1件落としている。

```
✗ 連絡が遅いプレイで得になる
```

「全社に証拠保全の周知を出す」（`communicate`）が、遅いプレイでも最大 +2点にしかならない。
原因は `evidence_preserved` が証拠19件で割られること。守れる2件では指標が 0.105 しか
動かず、重み 0.45 の証拠保全最優先でも総合 1.4点で、払った15分の被害増にほぼ相殺される。

**費用を時間だけにすると希釈に負ける**という一般則の実例なので、
直すときは方針の制約側（`forbid_action` / `require_before`）を使う案から検討する。
