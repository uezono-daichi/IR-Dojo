# シナリオの書き方

YAML を `scenarios/<id>.yaml` に置くだけで増える。Python は触らない。
DSL の全項目は [SPEC.md](../SPEC.md) Part 5、規約は Part 8 を参照。
ここは手順の要約である。

## 規模の目安

| 要素 | 個数 |
|---|---|
| 資産 | 5〜8 |
| アクション | 15〜20 |
| 証拠 | 10〜15（うち誤導 2〜3） |
| 未解消論点 | 3〜4（うち critical **3以上** — `unresolved_questions` の重み 0.40 はそれを前提にしている。SPEC 6.2 / 8.3） |
| フェーズ | **2（調査 → 封じ込め・対応）** |
| 方針 | 2〜3（**最低2つ必須**） |
| 想定プレイ時間 | 10分 |

この規模なら複雑度は 2〜3 に収まる。

## 手順

1. **真相を先に決める。** 誰がどこから侵入し、どう横展開し、何をしたか。
   これが `ground_truth.attack_narrative` になる
2. **資産と ground_truth を確定する。** `compromised` / `persistence` / `innocent`
3. **未解消論点を設計する。** 真相のうち「調べないと分からない部分」を切り出す。
   各論点に `implication`（未解消だと何が起きるか）を必ず書く
4. **証拠を設計する。** 本物のログ断片を書く。要約だけ返すと読解の訓練にならない
5. **誤導証拠を仕込む。** `innocent` の資産を指す、もっともらしい証拠。
   必ず `refuted_by` で棄却経路を用意する
6. **アクションを設計する。** `investigates` を正しく設定する（誤導測定に直結する）。
   そして `requires_evidence` で**手がかりの連鎖**を張る — 「これを思いつくには
   何を知っている必要があるか」。知らない資産は調べられない
7. **時間予算を設定する。** 全アクションの合計コストの4〜5割を
   `damage.acceleration.threshold_minutes` に
8. **方針を2つ以上書く。** 同じ真相に対して整合的な対応が変わるように
9. **複雑度を確認する。** ローダの算出値が狙いと違えば、誤導の数・`plausibility`・
   critical 論点の数で調整する
10. **hard で成立するか確認する。** 論点非表示・要約なしでも理不尽にならないか
11. **講評を書く。** 誤導の解説、`key_lessons`、再挑戦の提案

## 手がかりの連鎖

`requires_evidence` を書かないと、調査は**フラットなメニュー**になる。
何を発見しても選択肢が変わらず、「どれを選ぶか」ではなく
「どの順で全部やるか」の問題になってしまう。

```yaml
- id: act_memory_dump_ws042
  requires_evidence: [ev_001, ev_007]   # いずれか1つを持てば開く
```

**誤導証拠にも扉を開けさせる。** 本物だけが扉を開けるなら、
「増えた選択肢＝正しい道」になってシステムが正解を教えることになる。
誤導が指す資産を追う手段と、それを棄却する手段を同時に開けるのがよい。

**入口を1本にしない。** 唯一の入口を踏み外すと詰む。主要な資産には2経路。

**`contain` には書かない。** ローダが拒否する。証拠なしに基幹資産を止められること
自体は成立させ、当否は方針の制約で測る。

## 「取る必要のない情報」は存在しない

押しても何も返さないアクションを置かないこと。実務でやるべき調査を
「何も出ない罠」にすると、**探索そのものを避けることを教えてしまう。**

置くのは「取る必要がない情報」ではなく、
**「得られるが、いま決めたいことには効かない情報」**。

```yaml
- id: act_backup_integrity
  label: "バックアップの健全性を確認"
  yields: [ev_018]        # yields: [] にはしない
```
```yaml
- id: ev_018
  points_to: []           # 誰の侵害も示唆しない
  summary: "バックアップは健全で、暗号化前の世代から復元できる"
  content: |              # 中身は空にしない。ネガティブ所見も情報である
    ...
  reading: |
    ...
```
どの論点の `resolved_by` にも `refuted_by` にも入れない。
読めば分かることがあり、時間は確実に減り、被疑判定と論点には効かない。

`yields: []` が正当なのは、**先に壊してもう取れない場合だけ**である
（メモリを取る前に端末を停止した、など）。

## 陥りやすいところ

**実行の記録（`command`）は機構だけ書く。**
何を流したか、どれだけ捌いたか、どれだけかかったか。
**見つかったことは書かない** — それは証拠の側の仕事。
`command` は押した後にだけ返る（一覧には出ない）。押す前に配ると、
そこに書いた件数が機構ではなく結論になる（「0 detections」は
35分かけて買うはずの所見）。

**括弧で注記しない。** 「powered off（揮発性の情報はここで失われる）」は
システムが自分の罠に印を付ける行為である。失うものはラベルの動詞で言い、
説明が要るなら `description` と `reading` に置く。
括弧の中の名札（`(egress only)`、「携帯（登録番号）」）は資料なので通る。

**失われうる証拠にしか無い値を書かない。** 奪われた回にも記録は返るので、
そこに PID や件数が書かれていると、取り損ねたものを失った後に見せることになる。

**読み方は書く。結論は書かない。**
`Evidence.reading` にはログの読み方（EventID の意味、オプションの意味、
値の相場観）を書く。そこから何を結論するかは書かない。
`Action.description` も同じで、何をする作業かは書き、何が見つかるかは書かない。

| 書いてよい | 書いてはいけない |
|---|---|
| EventID 4104 は PowerShell のスクリプトブロックログ | だからこの端末は侵害されている |
| `-enc` は続く文字列が Base64 であることを示す | 攻撃者の常套手段なので疑うべき |
| 台帳の「平均転送量」は過去実績の平均 | だからこの通信は正常である |

読み方を隠すと**読解力**を測ってしまい、結論を書くと**推論を代行**してしまう。
どちらも「判断の健全性を測る」という主張を壊す（SPEC 1.4 / 3.10）。

**誤導証拠の reading を薄く書かない。** 本物だけ丁寧に書くと、
注釈の厚みがそのまま誤導の目印になる。

**0件を返す証拠は「どこを見て、どこを見ていないか」を書く。**
「何も見つからなかった」は所見であって資料ではない。
`content` は `hard` でも出るので、そこに要約を混ぜるとアシストが死ぬ。
**平常日テスト**: その行を、事案と無関係な平常日に同じツールを流しても
書けるか。書けるなら資料、書けないなら所見（SPEC 5.4）。

| 書いてよい | 書いてはいけない |
|---|---|
| 検査方式 : 既知シグネチャ照合 | 備考: シグネチャに一致するファイルは見つからなかった |
| 非対象 : ディスクに実体を残さない手法、未登録の検体 | 注: この端末に攻撃の痕跡は認められない |

**範囲欄を片側にだけ付けない。** 「非対象」が0件の証拠にしか付かないと、
欄の有無がそのまま「この資産は白」の印になる。

**`points_to` は「侵害を疑わせる資産」である。**
棄却に使う証拠（バックアップ設定、変更管理台帳など）は、誰も告発しない。
`points_to: []` にする。ここに資産を書くと、その資産が誤導測定から外れてしまう。

**棄却に使うアクションの `investigates` に、誤導証拠が指す資産を入れない。**
入れると、正しく棄却しに行った時間が「誤導追従」として数えられる。

**`destroys` は「以後取得できなくなる」という意味。**
取得済みの証拠は消えない。端末を停止しても、すでに取ったメモリダンプは手元に残る。
したがって排他は絶対ではなく**順序の問題**になる。

| 順序 | 結果 |
|---|---|
| メモリ → ディスクイメージ | 両方手に入る |
| ディスクイメージ → メモリ | メモリの情報は永久に取れない |

揮発性の高い順に採取するという実務の原則（RFC 3227）がそのまま効く。

**`destroys` はアクション名の動詞で言う。括弧書きで補わない。**
`ActionView` は `destroys` を学習者に渡さない。だからといって
「（揮発性証拠は失われます）」と注記すると、システムが自分の罠に印を付けることになる。
「ws-042 を**停止して**ディスクイメージを取得」なら、動詞だけで伝わる。

**注記を書きたくなったら、まずアクションの定義を疑う。**
ネットワーク隔離は端末を止めないので揮発性証拠は失われない。
注記で辻褄を合わせるのではなく、`destroys` を外すのが正しい。

**方針を切り替えたときに整合的な対応が変わるか、必ず確かめる。**
どの方針でも同じ行動が最適なら、この設計を使う意味がない。

## 公開に関する規約

| 対象 | 使うもの |
|---|---|
| IPv4 | `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`（RFC 5737） |
| ドメイン | `example.com`, `example.org`（RFC 2606）または `corp.local` |
| 組織名・人名 | 架空のもの |
| ハッシュ値 | 架空の値。実検体のハッシュを転記しない |

**実ログを転記しない。形式を真似て自分で書く。** 実ログには気づきにくい
識別子が残っていることがある。実行可能な検体を `scenarios/` に置かない。

実在の攻撃者名・マルウェアファミリ名は使ってよい（公開情報であり教育上の価値がある）。
ただし実在のインシデントを題材にする場合、被害組織が特定できる記述は避ける。

## 書いてはいけないこと

**`key_lessons` に対応の当否を書く。**
「fs01 は即座に隔離すべきでした」は越権である。方針の下でしか語れない。
書いてよいのは事実の開示、誤導の棄却手がかり、未解消論点の含意まで。

**棄却不能な誤導を置く。** 理不尽であり、学習者は「運が悪かった」としか受け取らない。
ローダが `refuted_by` の無い誤導証拠を拒否する。

**明らかに無関係な誤導を置く。** 誰も引っかからないので測定にならない。
